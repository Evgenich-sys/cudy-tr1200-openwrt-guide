# OpenWrt на Cudy TR1200 v1

[English version](README.en.md)

Руководство по установке и практической настройке **Cudy TR1200 v1**, составленное по результатам работы с OpenWrt 24.10.8.

Итоговая конфигурация включает:

- сеть через AmneziaWG с kill switch;
- отдельную Wi-Fi-сеть с прямым выходом в интернет;
- подключение роутера к гостиничному, домашнему или публичному Wi-Fi;
- приоритет Wi-Fi uplink над резервным Ethernet WAN;
- управление VPN боковым переключателем;
- белую/красную индикацию состояния VPN;
- резервное копирование, обновление, диагностику и восстановление.

> [!WARNING]
> Сторонняя прошивка может лишить гарантии или вывести устройство из строя. Инструкция предназначена только для **Cudy TR1200 hardware v1**. Перед началом проверьте модель и аппаратную ревизию на наклейке. Никогда не отключайте питание во время прошивки.

| Target | `ramips/mt76x8` |
| Проверенная версия | OpenWrt 24.10.8 (`r29233-443ec4032a`) |
| Официальный sysupgrade-образ | `openwrt-24.10.8-ramips-mt76x8-cudy_tr1200-v1-squashfs-sysupgrade.bin` |

Указанная контрольная сумма совпадает с официальным каталогом OpenWrt 24.10.8.

## 2. Какие образы нужны

Для первой установки используются два разных файла:

1. **Подписанный Cudy промежуточный образ** — принимается штатным веб-интерфейсом Cudy. В проверенном комплекте он назывался `TR1200-OpenWRT-Flash.bin`.
2. **Официальный sysupgrade-образ OpenWrt** — устанавливается после загрузки промежуточной прошивки.

Не загружайте обычный sysupgrade-образ прямо в штатный интерфейс Cudy. Получите у Cudy промежуточную прошивку именно для своей аппаратной ревизии. Образ от другой модели или варианта flash использовать нельзя.

Если OpenWrt уже установлен, для обычного обновления применяется только совместимый sysupgrade-образ. Промежуточная прошивка повторно не нужна.

## 3. Первая установка

### Подготовка

1. Убедитесь, что на наклейке указано **TR1200 v1**.
2. Скачайте у Cudy правильную подписанную промежуточную прошивку.
3. Скачайте официальный sysupgrade-образ для `cudy_tr1200-v1`.
4. Проверьте контрольную сумму sysupgrade-образа.
5. Соедините компьютер и роутер Ethernet-кабелем.
6. Сохраните настройки Cudy, если они могут понадобиться.
7. Используйте стабильное питание и не прошивайте через ненадёжный Wi-Fi.

Linux/macOS:

```sh
sha256sum openwrt-24.10.8-ramips-mt76x8-cudy_tr1200-v1-squashfs-sysupgrade.bin
```

Windows PowerShell:

```powershell
Get-FileHash .\openwrt-24.10.8-ramips-mt76x8-cudy_tr1200-v1-squashfs-sysupgrade.bin -Algorithm SHA256
```

### Этап A: с заводской Cudy на промежуточную OpenWrt

1. Откройте штатную панель управления Cudy.
2. Перейдите на страницу обновления прошивки.
3. Выберите подписанный Cudy файл `TR1200-OpenWRT-Flash.bin`.
4. Запустите обновление и подождите несколько минут.
5. Старая страница Cudy может не показать успешное завершение: вместо неё уже загружается OpenWrt.
6. Переподключитесь по Ethernet и откройте `http://<OPENWRT_DEFAULT_ADDRESS>`.

После первой загрузки OpenWrt беспроводная сеть может быть выключена, поэтому используйте Ethernet.

### Этап B: с промежуточной сборки на официальную OpenWrt

1. В LuCI откройте **System → Backup / Flash Firmware**.
2. Загрузите официальный файл `...cudy_tr1200-v1-squashfs-sysupgrade.bin`.
3. При переходе с промежуточной сборки на официальную **не сохраняйте настройки**.
4. Подтвердите обновление и дождитесь перезагрузки.
5. Снова откройте `http://<OPENWRT_DEFAULT_ADDRESS>` и сразу задайте надёжный пароль root.

Если проверка образа не проходит, остановитесь и ещё раз проверьте модель, ревизию, имя файла и версию промежуточной прошивки. Не используйте принудительное обновление, если этого прямо не требует актуальная инструкция OpenWrt для данного устройства и вы не понимаете риск.

## 4. Рекомендуемая схема travel-router

Проверенная конфигурация использует две локальные сети:

| Сеть | Пример подсети | Назначение | При падении VPN |
|---|---:|---|---|
| `lan` / VPN Wi-Fi | `<VPN_LAN_CIDR>` | Обычный трафик клиентов через AmneziaWG | Интернет блокируется |
| `direct` / Direct Wi-Fi | `<DIRECT_LAN_CIDR>` | Captive portal и диагностика без VPN | Работает через WAN |

Физические uplink-интерфейсы:

- `wwan`: Wi-Fi-клиент, основной uplink, metric `100`;
- Ethernet WAN: резервный uplink, metric `200`.

VPN-клиенты используют AmneziaWG. Клиенты Direct отдельным policy routing направляются напрямую в физический uplink.

```text
                    Интернет
                        |
            +-----------+-----------+
            |                       |
      Wi-Fi uplink              Ethernet WAN
       metric 100                metric 200
            |                       |
            +--------- zone wan ----+
                        |
              +---------+---------+
              |                   |
        AmneziaWG VPN       прямой маршрут
              |               table 100
        VPN Wi-Fi             Direct Wi-Fi
       kill switch             без VPN
```

Используйте собственные нейтральные SSID и уникальные сложные пароли. Не копируйте названия и учётные данные из чужих примеров.

## 5. Kill switch

Главная логика firewall:

- разрешить forwarding из `lan` в firewall-зону VPN;
- **не разрешать** прямой forwarding из `lan` в `wan`;
- разрешить `direct → wan`;
- не направлять `direct` в VPN-зону.

Проверка с клиента VPN-сети:

1. Включите VPN и убедитесь, что внешний IP относится к VPN-маршруту.
2. Выполните на роутере `ifdown VPN`.
3. Интернет в VPN Wi-Fi должен исчезнуть.
4. Direct Wi-Fi должен продолжить работать при исправном uplink.
5. Выполните `ifup VPN` и проверьте восстановление.

Если VPN Wi-Fi продолжает выходить в интернет при выключенном туннеле, kill switch не работает. Ищите ошибочное правило `lan → wan`.

## 6. Direct и смена внешней сети

Direct нужен для captive portal в гостинице и диагностики. Policy rule направляет трафик Direct-подсети в таблицу `100`, где находится default route через физический uplink.

Проверка:

```sh
ip rule
ip route show table 100
ubus call network.interface.wwan status
ip -4 route show default
```

Не фиксируйте домашний или гостиничный gateway в конфигурации. При подключении к другой сети адрес шлюза обычно меняется. Обновляйте таблицу `100` по default route, полученному через DHCP, либо автоматизируйте это проверенным netifd hotplug-скриптом.

Для captive portal:

1. подключите телефон или ноутбук к Direct Wi-Fi;
2. подключите `radio1` как Station к внешнему Wi-Fi, назначив интерфейс `wwan` и firewall-зону `wan`;
3. откройте обычную HTTP-страницу, чтобы вызвать портал;
4. пройдите авторизацию;
5. включите и проверьте VPN-сеть.

## 7. Боковой переключатель VPN

На проверенном устройстве боковой переключатель создаёт hotplug-события `BTN_0`. Создайте `/etc/hotplug.d/button/99-slider-vpn`:

```sh
#!/bin/sh

[ "$BUTTON" = "BTN_0" ] || exit 0

case "$ACTION" in
    pressed)
        logger -t slider-vpn "VPN ON"
        ifup VPN
        ;;
    released)
        logger -t slider-vpn "VPN OFF"
        ifdown VPN
        ;;
esac
```

Сделайте файл исполняемым:

```sh
chmod +x /etc/hotplug.d/button/99-slider-vpn
```

Проверьте события:

```sh
logread -f | grep -E 'slider-vpn|BTN_0|button'
```

Если направление переключателя на вашем экземпляре обратное, поменяйте местами `ifup VPN` и `ifdown VPN`.

## 8. LED-индикация VPN

На проверенном устройстве использовались:

- `/sys/class/leds/white:status`;
- `/sys/class/leds/red:power`.

Логика:

- белый горит постоянно — VPN поднят, контрольный трафик проходит;
- белый мигает — интерфейс поднят, но проверка трафика не проходит;
- красный горит постоянно — VPN выключен.

Пример монитора находится в [`scripts/vpn-led-monitor`](scripts/vpn-led-monitor). Имена LED могут измениться, поэтому сначала выполните `ls /sys/class/leds/`. Публичный DNS-адрес используется только для проверки связи и при необходимости может быть заменён.

## 9. Ограничения ресурсов

У TR1200 v1 мало RAM и flash. В проверенной конфигурации:

- внутренний writable overlay составлял около 9,6 МиБ;
- после основной настройки оставалось около 7 МиБ;
- обычно было доступно около 55 МиБ RAM;
- Tailscale работал, но расходовал слишком много памяти;
- swap/zram не поддерживался проверенной конфигурацией ядра;
- USB extroot работал, но после удаления тяжёлых сервисов оказался не нужен.

Рекомендации:

- перед установкой пакетов проверяйте `free -m` и `df -h /overlay`;
- не выполняйте массовый `opkg upgrade`;
- переходите между версиями прошивки через sysupgrade;
- устанавливайте только необходимые сервисы;
- используйте kernel modules строго от запущенной версии ядра.

## 10. Backup и обновление

Перед существенными изменениями создавайте backup:

```sh
umask 077
sysupgrade -k -b /tmp/cudy-tr1200-backup.tar.gz
sha256sum /tmp/cudy-tr1200-backup.tar.gz
```

Сразу скачайте архив: `/tmp` находится в RAM и очищается при перезагрузке.

> [!CAUTION]
> Backup может содержать пароли Wi-Fi, приватные и preshared VPN-ключи и другие секреты. Никогда не публикуйте его на GitHub и не прикладывайте к открытым issue.

Перед sysupgrade:

```sh
ubus call system board
df -h /overlay
free -m
sysupgrade -k -b /tmp/pre-upgrade-backup.tar.gz
```

Проверьте точное соответствие образа модели, изучите release notes и убедитесь, что AmneziaWG доступен для нового ядра. После обновления протестируйте обе Wi-Fi-сети и kill switch.

## 11. Диагностика

```sh
date
uptime
free -m
df -h /overlay
ubus call system board
ifstatus VPN
ubus call network.interface.wwan status
ip addr
ip rule
ip route
ip route show table 100
logread | tail -n 120
dmesg | tail -n 120
```

Перед публикацией вывода удалите SSID, MAC-адреса, публичные IP, hostname, серийные номера, ключи и учётные данные.

Быстрая логика поиска проблемы:

- Direct работает, VPN Wi-Fi нет — проверяйте VPN, доступность endpoint, маршруты и логи;
- не работает ни одна сеть — проверяйте физический uplink и DHCP gateway;
- Direct сломался после смены гостиницы — ищите старый gateway в table `100`;
- VPN Wi-Fi работает при выключенном VPN — немедленно исправьте kill switch;
- остаётся слишком мало RAM — остановите или удалите тяжёлые процессы.

## 12. Failsafe и восстановление

Failsafe OpenWrt позволяет исправить network/firewall или сменить забытый пароль root:

1. подключитесь по Ethernet;
2. войдите в failsafe в начале загрузки согласно актуальной инструкции OpenWrt;
3. если DHCP выключен, задайте компьютеру статический адрес;
4. подключитесь к failsafe-адресу роутера;
5. выполните `mount_root` и исправьте только нужные файлы;
6. перезагрузите устройство.

Пример:

```sh
mount_root
passwd
vi /etc/config/network
vi /etc/config/firewall
reboot -f
```

Не придумывайте последовательность TFTP/Reset: восстановление через bootloader зависит от конкретного устройства. Для возврата на Cudy firmware используйте актуальную инструкцию Cudy; у TR1200 есть особые требования к используемому Ethernet-порту.

## 14. Подробная настройка сети

### 14.1. Имена и роли интерфейсов

В руководстве используются не реальные адреса, а обозначения:

| Обозначение | Что подставить у себя |
|---|---|
| `<OPENWRT_DEFAULT_ADDRESS>` | Стандартный адрес свежей OpenWrt из официальной документации |
| `<VPN_ROUTER_ADDRESS>` | Адрес роутера в основной VPN-сети |
| `<VPN_LAN_CIDR>` | Подсеть основной клиентской сети |
| `<DIRECT_ROUTER_ADDRESS>` | Адрес роутера в Direct-сети |
| `<DIRECT_LAN_CIDR>` | Подсеть прямой клиентской сети |
| `<UPLINK_GATEWAY>` | Шлюз, полученный текущим uplink через DHCP |
| `<VPN_TEST_HOST>` | Выбранный узел для проверки передачи трафика через VPN |

Логическая схема интерфейсов:

| Интерфейс | Протокол | Устройство/роль | Firewall zone |
|---|---|---|---|
| `lan` | static | bridge и основной локальный AP | `lan` |
| `direct` | static | второй локальный AP | `direct` |
| `wwan` | DHCP client | внешний Wi-Fi в режиме Station | `wan` |
| `wan` | DHCP client | Ethernet WAN | `wan` |
| `VPN` | `amneziawg` | VPN-туннель | `awg` |

Основную локальную подсеть меняли до настройки остальных компонентов. Это важно: после применения нового адреса старая вкладка LuCI перестаёт отвечать, компьютер должен заново получить DHCP lease, а панель нужно открыть уже по `<VPN_ROUTER_ADDRESS>`.

### 14.2. Настройка Wi-Fi uplink через LuCI

1. Откройте **Network → Wireless**.
2. На радиомодуле, выбранном для внешнего подключения, нажмите **Scan**.
3. Выберите внешнюю сеть и нажмите **Join Network**.
4. Введите пароль, не сохраняя его в заметках или публичных скриншотах.
5. Назначьте подключение новой логической сети `wwan`.
6. Для `wwan` выберите DHCP client и firewall zone `wan`.
7. Примените изменения и дождитесь адреса, gateway и DNS от внешней сети.
8. Проверьте состояние:

```sh
ubus call network.interface.wwan status
ip link show
ip route
iwinfo 2>/dev/null
```

При публикации результата `ubus`, `ip` или `iwinfo` удаляйте SSID, BSSID/MAC, адреса, hostname и lease-информацию.

### 14.3. Приоритет uplink

В испытанной схеме Wi-Fi uplink имел меньшую метрику и был основным, а Ethernet WAN — большую и служил резервом. Конкретные числа не принципиальны; важно, чтобы:

- метрики были разными;
- маршрут к VPN endpoint всегда шёл через работающий физический uplink;
- сам VPN не пытался достичь своего endpoint через собственный туннель;
- после смены uplink таблица маршрутов пересчитывалась корректно.

Проверка:

```sh
ip route
ip route get <VPN_ENDPOINT_ADDRESS>
```

Команду со значением endpoint не публикуйте вместе с результатом.

## 15. AmneziaWG и VPN-сеть

### 15.1. Что переносится из профиля

Для интерфейса `VPN` требуются параметры экспортированного AmneziaWG-профиля: адрес интерфейса, peer, endpoint, allowed IPs и дополнительные параметры протокола. Приватный ключ и preshared key вводятся только на роутере и не должны попадать в Git, backup без защиты, скриншоты или диагностические сообщения.

Порядок работы:

1. Найдите сборку AmneziaWG, совместимую с точной версией OpenWrt и ядра.
2. Установите пользовательский пакет и соответствующий kernel module.
3. Создайте интерфейс с именем `VPN`.
4. Перенесите параметры из собственного профиля.
5. Добавьте интерфейс в отдельную firewall-зону `awg`.
6. Разрешите forwarding только из основной локальной зоны в `awg`.
7. Поднимите интерфейс и проверьте handshake, маршруты и передачу данных.

Не приводятся универсальные команды установки пакета: репозиторий и имена пакетов зависят от версии OpenWrt и AmneziaWG. Установка kernel module от другой версии ядра может сделать сеть нестабильной.

### 15.2. Проверки VPN

```sh
ifstatus VPN
ifup VPN
ifdown VPN
ip route
ping -I VPN -c 3 <VPN_TEST_HOST>
logread | grep -Ei 'amnezia|wireguard|VPN|netifd' | tail -n 100
```

Поле `up=true` ещё не доказывает, что туннель передаёт трафик. Поэтому LED-монитор и ручная диагностика выполняют отдельную проверку через интерфейс `VPN`.

### 15.3. Если VPN не поднимается

1. Сначала проверьте Direct-сеть. Если она тоже без интернета, проблема находится в uplink, а не в VPN.
2. Убедитесь, что часы и часовой пояс корректны.
3. Проверьте физический маршрут к endpoint.
4. Сравните установленный kernel module с текущим `uname -r`.
5. Перезапустите интерфейс: `ifdown VPN; sleep 2; ifup VPN`.
6. Изучите `logread` и `dmesg`, предварительно скрыв идентификаторы.
7. Если сервер или ключи менялись, экспортируйте новый профиль вместо случайной правки старого.

## 16. Direct, policy routing и captive portal

### 16.1. Почему одной сети недостаточно

Если весь трафик роутера направлен в VPN, страница авторизации гостиницы может не открыться: до завершения captive portal внешний интернет ещё недоступен. Direct-сеть решает эту проблему, не отключая защиту для остальных клиентов.

Для `direct` создаются:

- отдельный интерфейс со своей подсетью и DHCP server;
- отдельный AP;
- firewall-zone `direct`;
- forwarding `direct → wan`;
- policy rule по source network или incoming interface;
- отдельная routing table с default route через физический uplink.

### 16.2. Проверка policy routing

```sh
ip rule
ip route show table 100
ip -4 route show default
```

Ожидаемая логика, без привязки к конкретным адресам:

```text
from <DIRECT_LAN_CIDR> lookup 100
table 100 default via <UPLINK_GATEWAY> dev <UPLINK_DEVICE>
```

Главный найденный недостаток первоначальной реализации — статический gateway в table `100`. Он работал в одной сети, но становился неверным после поездки. Для travel-router шлюз следует брать из фактического DHCP route.

Временная замена после проверки текущего gateway:

```sh
ip route replace table 100 default via <UPLINK_GATEWAY> dev <UPLINK_DEVICE>
```

Для постоянной автоматизации можно использовать netifd hotplug, но скрипт нужно проверить при подключении и отключении обоих uplink. Он не должен оставлять старый маршрут или конкурировать со статической настройкой LuCI.

### 16.3. Порядок подключения в гостинице

1. Подключитесь к Direct Wi-Fi.
2. В LuCI просканируйте сети на uplink-радиомодуле.
3. Подключите `wwan` к гостиничной сети.
4. Убедитесь, что интерфейс получил DHCP-параметры.
5. Проверьте и при необходимости обновите default route в table `100`.
6. Откройте обычную HTTP-страницу и пройдите captive portal.
7. Убедитесь, что Direct-клиент получил интернет.
8. Включите VPN и проверьте основную сеть.
9. Повторно протестируйте kill switch.

## 17. Firewall: итоговая матрица

| Источник | Назначение | Разрешение | Причина |
|---|---|---|---|
| `lan` | `awg` | Да | Основной доступ через VPN |
| `lan` | `wan` | Нет | Kill switch |
| `direct` | `wan` | Да | Captive portal и прямой доступ |
| `direct` | `awg` | Нет | Direct не должен незаметно уйти в VPN |
| `wan` | LuCI/SSH | Нет | Админка не открывается внешней сети |
| внутренние сети | роутер | По необходимости | DHCP, DNS и администрирование |

В зоне `wan` обычно используется masquerading. Для VPN-зоны параметры NAT и MTU зависят от пакета и профиля. После каждого изменения firewall проверяйте не только наличие интернета, но и отрицательный сценарий: при выключенном VPN основная сеть обязана потерять внешний доступ.

## 18. Ежедневное использование

### Обычный запуск

1. Подайте питание и дождитесь полной загрузки.
2. Дождитесь подключения `wwan` или Ethernet WAN.
3. Установите боковой переключатель в положение VPN ON.
4. Подключите устройства к основной VPN Wi-Fi.
5. Проверьте LED: постоянный белый означает успешную проверку туннеля.

Быстрый контроль:

```sh
uptime
free -m
df -h /overlay
ifstatus VPN
ubus call network.interface.wwan status
ip route
```

### Когда нужен интернет без VPN

Предпочтительный вариант — временно подключить конкретное устройство к Direct Wi-Fi. Глобальное выключение VPN боковым переключателем не должно выпускать клиентов основной сети напрямую: их соединение блокирует kill switch.

### Проверка аппаратного переключателя

```sh
logread -f | grep -E 'slider-vpn|BTN_0|button'
```

Скрипт переключателя нужно добавить в `/etc/sysupgrade.conf`, иначе нестандартный файл может исчезнуть после обновления.

## 19. LED-служба через procd

Одного файла `vpn-led-monitor` недостаточно: для автоматического запуска создаётся init script `/etc/init.d/vpn-led`.

```sh
#!/bin/sh /etc/rc.common

USE_PROCD=1
START=95
STOP=10

start_service() {
    procd_open_instance
    procd_set_param command /usr/bin/vpn-led-monitor
    procd_set_param respawn 3600 5 5
    procd_close_instance
}

stop_service() {
    echo none > /sys/class/leds/white:status/trigger 2>/dev/null
    echo 0 > /sys/class/leds/white:status/brightness 2>/dev/null
}
```

Установка:

```sh
chmod +x /usr/bin/vpn-led-monitor /etc/init.d/vpn-led
/etc/init.d/vpn-led enable
/etc/init.d/vpn-led restart
```

Перед копированием проверьте реальные имена в `/sys/class/leds/`. Раннее мигание во время boot может управляться самой платформой; пользовательская логика начинает действовать после запуска сервиса.

## 20. Эксперименты и выводы

### USB extroot

USB-накопитель был успешно отформатирован в ext4 и использован как `/overlay`. Это подтвердило работоспособность USB storage, `block-mount` и ext4. После удаления тяжёлых пакетов внутреннего overlay снова стало достаточно, поэтому от extroot отказались: постоянная флешка добавляла точку отказа и усложняла восстановление.

Перед возвратом на внутренний overlay сравнивались критичные конфиги и пользовательские скрипты. Затем extroot отключили во внутреннем `fstab`, загрузились без USB и повторно проверили VPN, RAM и writable overlay.

### Swap и zram

Проверенная сборка ядра не предоставляла поддержку swap. Поэтому ни swap-файл на USB, ни zram не могли работать без другого kernel configuration. Создавать большой swap-файл «на всякий случай» бессмысленно и создаёт лишнюю запись на накопитель.

### Tailscale

Tailscale был установлен и функционально работал, включая удалённый доступ. Но `tailscaled` потреблял слишком большую долю доступной RAM для устройства этого класса. После удаления демона, его firewall-настроек и больше не нужных зависимостей запас памяти заметно вырос.

Практический вывод: тяжёлый remote-access daemon лучше запускать на более мощном устройстве в локальной сети. На TR1200 следует оставлять только необходимые службы.

## 21. Backup и восстановление конфигурации

Перед созданием архива проверяйте список:

```sh
sysupgrade -l
```

В backup должны попадать как минимум основные UCI-конфиги и пользовательские файлы:

```text
/etc/config/network
/etc/config/wireless
/etc/config/firewall
/etc/hotplug.d/button/99-slider-vpn
/etc/init.d/vpn-led
/usr/bin/vpn-led-monitor
```

Нестандартные пути добавляются в `/etc/sysupgrade.conf`. Опция `sysupgrade -k -b` сохраняет также сведения об установленных пакетах, но сам backup не содержит готовые бинарные пакеты для любого ядра. После чистой установки AmneziaWG и другие модули может потребоваться установить заново.

Восстанавливайте архив только на совместимой версии. После восстановления проверьте:

1. наличие нужных пакетов и kernel modules;
2. обе Wi-Fi-сети и DHCP;
3. `wwan`, маршруты и table `100`;
4. VPN handshake и передачу трафика;
5. kill switch;
6. переключатель и LED-службу.

## 22. Обновление OpenWrt

Перед обновлением:

1. Снимите новый backup и скачайте его из `/tmp`.
2. Сохраните список установленных пакетов.
3. Проверьте свободную flash и RAM.
4. Убедитесь, что образ предназначен именно для TR1200 v1.
5. Сверьте SHA-256 с официальным источником.
6. Проверьте доступность AmneziaWG для нового ядра.
7. По возможности подключитесь по Ethernet.
8. Не выполняйте обновление при нестабильном питании.

После обновления:

```sh
ubus call system board
uname -r
df -h /overlay
free -m
ifstatus VPN
ip rule
ip route
ip route show table 100
logread | tail -n 100
```

Не выполняйте массовый `opkg upgrade`: пакеты ядра жёстко связаны с версией kernel. Для перехода между релизами используйте sysupgrade.

## 23. Windows: когда проблема находится не в роутере

Во время настройки был обнаружен ошибочный default route на Windows. Из-за него доступ выглядел сломанным, хотя OpenWrt работал правильно. Диагностика:

```powershell
ipconfig /all
route print
Get-NetRoute -AddressFamily IPv4 |
    Sort-Object DestinationPrefix, RouteMetric
Get-NetIPConfiguration
```

Порядок проверки:

1. Убедитесь, что клиент получил адрес и gateway от выбранной сети роутера.
2. Проверьте доступность `<VPN_ROUTER_ADDRESS>` или `<DIRECT_ROUTER_ADDRESS>`.
3. Проверьте внешний адрес без DNS.
4. Отдельно проверьте DNS-имя.
5. Посмотрите, нет ли старого persistent default route через другой адаптер.

Не удаляйте все default routes вслепую. Сначала определите неверную запись по `InterfaceIndex`, `NextHop` и метрике, затем удаляйте только её через `Remove-NetRoute`.

## 24. Диагностика по симптомам

| Симптом | Вероятная причина | Что проверить сначала |
|---|---|---|
| VPN Wi-Fi без интернета, Direct работает | VPN, endpoint или маршрут | `ifstatus VPN`, route к endpoint, `logread` |
| Обе сети без интернета | Физический uplink | статус `wwan`, DHCP, default route |
| Direct сломался после смены сети | Старый gateway в table `100` | `ip rule`, `ip route show table 100` |
| Основная сеть работает при VPN OFF | Нарушен kill switch | отсутствие forwarding `lan → wan` |
| Белый LED мигает | Интерфейс up, проверка трафика не проходит | ping через `VPN`, routes и logs |
| LuCI не открывается, но роутер доступен | `uhttpd` или firewall | `/etc/init.d/uhttpd status` |
| Быстро заканчивается flash | Лишние пакеты или данные overlay | `df`, `du` по `/overlay/upper` |
| Очень мало available RAM | Тяжёлый daemon | `free`, `top` |
| После обновления нет VPN | Нет совместимого модуля | `uname -r`, список пакетов, `dmesg` |
| Потерян доступ после правки сети | Ошибка UCI/firewall | OpenWrt failsafe и `mount_root` |

Универсальный диагностический набор:

```sh
date
uptime
free -m
df -h /overlay
ubus call system board
ifstatus VPN
ubus call network.interface.wwan status
ip link
ip rule
ip route
ip route show table 100
logread | tail -n 120
dmesg | tail -n 120
```

Перед публикацией замените все идентификаторы плейсхолдерами. Даже если команда не показывает ключ напрямую, в логах могут находиться SSID, MAC, endpoint, адреса и hostname.

## Проверка безопасности

- Задайте сложный уникальный пароль root.
- Не открывайте LuCI и SSH в `wan`/`wwan`.
- Не публикуйте `/etc/config/network` без проверки на приватные ключи.
- Никогда не публикуйте backup роутера.
- Перевыпустите VPN-ключи при подозрении на утечку.
- Читайте сторонние скрипты перед запуском.
- Храните офлайн-копию для восстановления и проверенные контрольные суммы.
